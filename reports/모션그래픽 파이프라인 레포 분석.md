# HyperFrames 위에 motionmaxxing의 연출 규율을 얹어라

새 레포의 렌더링 코어는 **HyperFrames(HeyGen, Apache-2.0)**로 하고, 그 위에 직접 만든 연출·게이트 레이어를 올리는 구성을 권장한다. 연출 레이어는 **motionmaxxing**의 수치화된 모션 법칙과 HyperFrames 공식 스킬의 story → SPEC → review 루프를 합쳐서 만든다. 사용자가 "motion-maxxing"이라고 부른 레포의 실제 이름은 하이픈 없는 `Tejashmakwana/motionmaxxing`이다. 24일 만에 별 1,134개를 받았지만 커밋이 2개뿐인 일회성 공개본이라서 의존성으로 쓰기는 어렵고, 연출 지식을 뽑아 쓸 참고 자료로 보는 편이 맞다. 의존해도 되는 레포는 생각보다 적다. 공식 엔진(HyperFrames, Remotion), 공식 스킬 팩(hyperframes skills, remotion-dev/skills), 동료 심사를 거친 연구 파이프라인(Code2Video, TheoremExplainAgent, Paper2Video) 정도다. 2026년 9~10월에 몰려 나온 개인 스킬 팩들은 아이디어 출처로만 쓰는 것이 안전하다. 라이선스 위험은 Remotion(4인 이상 회사는 유료이고 5.0부터 계약직도 인원에 포함)과 한국어 TTS에 집중되어 있다. F5-TTS, XTTS-v2, MusicGen 가중치는 비상업 라이선스다. 한국어 내레이션은 **Qwen3-TTS(Apache-2.0, 한국어 지원)**로 생성하고, 자막 타이밍은 **WhisperX의 한국어 wav2vec2 강제 정렬**로 잡으면 상업적으로 깨끗한 경로가 된다. 이들 레포 중 어느 것도 독립적인 품질 벤치마크를 받지 않았다. 그러니 "방송급"을 결정하는 것은 레포 선택이 아니라 사용자가 직접 설계하는 승인 게이트와 QA 규칙이다.

## motionmaxxing은 소프트웨어가 아니라 470KB짜리 연출 교본이다

motionmaxxing은 Claude Code용 SKILL.md 스킬 하나로 되어 있다. 2026-10-06에 커밋 2개로 공개되었고 2026-10-30 기준 별 1,134개, 포크 108개, 열린 이슈 1개, 라이선스 Apache-2.0이다 ([repo](https://github.com/Tejashmakwana/motionmaxxing)). 사용자가 쓴 하이픈 표기 "motion-maxxing"으로 검색하면 관련 레포가 나오지 않고 스팸 레포만 걸린다. 같은 이름을 쓰는 파생 레포들은 모두 별 0~2개이며, 포크 중 10-06 이후 푸시된 것은 하나도 없다 ([GitHub search](https://github.com/search?q=motionmaxxing&type=repositories)). README도 상태를 "early release"로 적고 있고, 작성자의 컴퓨터에서 몇 건의 실제 브리프에 써 본 수준이며 넓게 테스트하지는 않았다고 밝힌다 ([README](https://github.com/Tejashmakwana/motionmaxxing/blob/main/README.md)). 이 스킬은 Remotion을 쓰지 않는다. 순수 HTML 위에 GSAP 3.12.5를 벤더링한 seek-safe 런타임 `runtime/motion.js`를 올리고, Chrome DevTools 프로토콜과 ffmpeg로 프레임 단위 렌더링을 한다. HyperFrames와의 호환도 명시되어 있다 ([runtime/README](https://github.com/Tejashmakwana/motionmaxxing/blob/main/runtime/README.md), [SKILL.md](https://github.com/Tejashmakwana/motionmaxxing/blob/main/SKILL.md)).

쓸 만한 부분은 엔진 쪽이 아니라 지식 쪽이다. `references/`의 14개 파일(약 470KB)과 SKILL.md에 들어 있는 규칙들이 그렇다. 작성자는 실제 런칭 필름에서 53개 "프로 모먼트"를 GSAP로 재현했고 4,288개의 움직임을 측정해 **12개의 이름 붙은 이징**으로 정리했다고 주장한다. 이징 사용 비율은 cruise 18%, glide 14%, softInOut 14% 순이다. 측정값으로는 중앙값 이동 10프레임(0.33초), 오버슛 8.8%, 형제 요소 stagger 3프레임, 엔드 홀드 0.6~1.4초를 제시한다. 다만 원본 코퍼스는 비공개라서 검증할 수 없다 ([HOW-IT-WAS-BUILT](https://github.com/Tejashmakwana/motionmaxxing/blob/main/docs/HOW-IT-WAS-BUILT.md)). 검증 가능한 쪽은 SKILL.md에 적힌 12개 연출 법칙이다. 비트마다 하나의 믿음을 산다, 움직임 위에서 컷한다, 착지는 감속하고 퇴장은 가속한다, 거의 아무것도 페이드하지 않는다 같은 규칙이다. 여기에 페이지 크롬, "02 / SPEAK" 같은 카운터, 덱 레이아웃, 슬로건 카피를 금지하는 **"never ship" 목록**과 스크립트로 구현된 **G0~G5 게이트**가 붙는다. G2는 평평한 프레임이 3개 넘게 이어지면 안 된다는 규칙이고, G3은 엔드 홀드 1.4초 이하 규칙이며, G5는 DOM 린트다. 납품물에는 게이트 수치를 인용하되 품질을 스스로 인증하지 않는 **NOTE.md**가 반드시 포함되어야 한다 ([SKILL.md](https://github.com/Tejashmakwana/motionmaxxing/blob/main/SKILL.md)).

품질 증거는 모두 작성자 본인이 만든 것이다. 비포/애프터 영상 3개와 블라인드 A/B 결과 "10번 중 9번"이 있는데, README도 평가자가 한 명이라서 "벤치마크가 아니라 신호"라고 인정한다 ([README](https://github.com/Tejashmakwana/motionmaxxing/blob/main/README.md)). 379개 레포를 정리한 awesome-claude-video-skills 목록은 motionmaxxing의 보안 등급을 "SAFE"로 매겼지만, 16개 스킬을 실제로 돌려 본 테스트에는 넣지 않았다 ([awesome-claude-video-skills](https://github.com/zhuyansen/awesome-claude-video-skills)). 그래도 이 레포의 타이밍 원칙에는 무게가 있다. HyperFrames 공식 스킬의 `motion.md`가 HeyGen 런칭 필름을 프레임 단위로 측정해서 독자적으로 거의 같은 결론에 도달했기 때문이다. 내용은 "Arrive slow, leave clean", 퇴장은 진입보다 40~50% 짧게, 글자 stagger는 1프레임, 가장 빠른 프레임에서 컷, 모든 요소에 `power2.out` 0.5초를 똑같이 쓰면 "생성된 티가 난다"는 것이다 ([motion.md](https://github.com/heygen-com/hyperframes/blob/main/skills/hyperframes/references/motion.md)). 두 출처가 따로 같은 수치에 도달했다는 점이 이 값들을 기본값으로 삼을 근거가 된다.

"고유한 룩"이 있다는 평은 HyperFrames(23.5분)와 Barty-Bart(4.7분)만 받았다. 평가자는 한 명이었다 ([awesome-claude-video-skills](https://github.com/zhuyansen/awesome-claude-video-skills), [RESULTS.md](https://github.com/zhuyansen/agent-skills-hub/blob/main/ops/video-runs/RESULTS.md)). 공식 Remotion 스킬은 렌더가 깨지지 않게 해 주지만 취향(taste)을 담고 있지 않다. 그래서 연출 레이어는 사용자가 직접 써야 한다.

에이전트 파이프라인 구조가 효과적이라는 가장 강한 증거는 Code2Video 논문에 있다. 같은 Claude Opus 4.1을 썼을 때 planner/coder/critic 구조는 Aesthetics 87.9, TeachQuiz 86.0을 기록했고, 직접 코드 생성은 37.8과 40.0에 그쳤다. 대신 시간은 영상당 13.8분 대 2.8분, 토큰은 43.1K 대 2.3K가 들었다 ([arXiv 2510.01174](https://arxiv.org/html/2510.01174)). 약 5배의 시간과 19배의 토큰을 써서 점수가 약 2배가 된 것이다. TheoremExplainAgent는 "대부분의 영상에 시각 요소 레이아웃의 사소한 문제가 있다"고 보고했다 ([arXiv 2502.19400](https://arxiv.org/abs/2502.19400)). PhysicsSolutionAgent도 레이아웃 불일치를 주된 실패로 꼽았다 ([arXiv 2601.13453](https://arxiv.org/abs/2601.13453)). 에이전트가 만든 모션그래픽에서 가장 흔한 실패는 **레이아웃**이고, QA에 처음 투자할 곳도 여기다.

## 렌더링 엔진은 HyperFrames를 기본으로, Remotion은 조건부로 쓴다

2026년 10월 말 기준으로 활발히 개발되면서 실제 생산 규모로 쓰이는 엔진은 세 개다. Remotion v4.0.539는 React 기반 source-available이고, HyperFrames v0.8.221은 HTML+GSAP 기반 Apache-2.0이며, ManimCE v0.22.1은 Python 기반 MIT다 ([Remotion](https://github.com/remotion-dev/remotion), [HyperFrames](https://github.com/heygen-com/hyperframes), [ManimCE](https://github.com/ManimCommunity/manim)). Remotion과 HyperFrames는 렌더링 경로가 같다. 헤드리스 Chrome으로 프레임을 찍고 FFmpeg로 인코딩한다. 따라서 Chrome이 그릴 수 있는 CSS, SVG, Canvas, WebGL, Lottie는 모두 쓸 수 있고, 결과물 품질의 상한도 두 엔진이 같다 ([HyperFrames vs Remotion guide](https://hyperframes.heygen.com/guides/hyperframes-vs-remotion)).

HyperFrames를 기본으로 권하는 근거는 네 가지다. 첫째, 라이선스가 Apache-2.0이고 "렌더당 비용이나 상업 사용 기준선이 없다" ([README](https://github.com/heygen-com/hyperframes)). 둘째, 에이전트를 전제로 설계되었다. 비대화형 CLI, 린터, 스킬 7개, Claude Code 플러그인(`claude plugin marketplace add heygen-com/hyperframes`), 약 450개 블록의 레지스트리를 갖추고 있다. 셋째, 공식 스킬에 사용자가 원하는 단계별 승인 구조가 이미 들어 있다. 15초가 넘는 영상이면 스토리라인 세 개 중 하나를 사람이 고르고, `SPEC.md`에서 "모든 형용사를 숫자로" 바꾸고, `check --json`과 `snapshot --review`를 거친 다음, 사람이 Studio 미리보기를 승인해야 렌더한다 ([SKILL.md](https://github.com/heygen-com/hyperframes/blob/main/skills/hyperframes/SKILL.md)). 넷째, motionmaxxing이 HyperFrames 호환을 선언하고 있어서 두 자산을 같은 HTML 위에서 합칠 수 있다. HeyGen 자체 제품과 tldraw 등이 이미 HyperFrames를 생산에 쓰고 있다 ([ADOPTERS.md](https://github.com/heygen-com/hyperframes/blob/main/ADOPTERS.md)).

위험도 분명하다. HyperFrames는 2026-03-10에 생성된 v0.x 소프트웨어이고 하루에 여러 번 릴리스되므로 API가 자주 바뀐다. 결정론 계약(paused timeline, 벽시계 금지, 시드 없는 난수 금지)은 HyperFrames 가이드 자신이 말하듯 **"조용히 실패"**한다. Remotion의 "프레임 번호의 순수 함수" 모델은 실패할 때 더 크게 드러난다 ([HyperFrames vs Remotion guide](https://hyperframes.heygen.com/guides/hyperframes-vs-remotion)). 그러니 버전을 고정하고, motionmaxxing의 `Motion.selfTest`처럼 같은 프레임을 두 번 렌더해서 비교하는 회귀 테스트를 반드시 넣어야 한다. 커뮤니티에서는 HyperFrames가 토큰을 많이 쓰고 디자인이 약하다는 일화도 있지만 검증된 내용은 아니다 ([cutback.video](https://cutback.video/blog/hyperframes-vs-remotion-vs-selects)). 두 엔진을 직접 비교한 실행은 HeyGen이 쓴 단일 실행뿐이다. Remotion 12분 30초, HyperFrames 11분 50초였고, 문서 스스로 "한 번의 실행으로는 품질에 대해 아무것도 결정할 수 없다"고 적었다 ([HyperFrames vs Remotion guide](https://hyperframes.heygen.com/guides/hyperframes-vs-remotion)).

Remotion은 사용자가 이미 한 번 썼다가 버린 엔진이고, 선택 여부는 라이선스 조건에 달려 있다. 개인이나 직원 3명 이하 회사라면 무료로 상업 영상을 만들 수 있고, 생태계와 Lambda 분산 렌더링은 가장 성숙하다(리전당 동시 실행 기본 1,000개) ([LICENSE.md](https://github.com/remotion-dev/remotion/blob/main/LICENSE.md), [Lambda limits](https://www.remotion.dev/docs/lambda/limits)). 애니메이션 레이어로 보면 `interpolate`/`spring`/`Easing`과 `@remotion/paths`·`shapes`·`noise`·`layout-utils`·`motion-blur`가 MIT 순수 함수라서 가장 안전한 기반이다. `@remotion/transitions`(프레젠테이션 23종)와 `@remotion/effects`(약 80종)는 MIT가 아니라 Remotion License로 묶여 있다 ([Remotion packages](https://github.com/remotion-dev/remotion/tree/main/packages), [effects docs](https://www.remotion.dev/docs/effects)). ManimCE는 수식과 다이어그램 장면에만 쓰는 보조 렌더러로 두고, ProRes/mov 알파 레이어로 합성하는 방식이 적절하다. Manim용 에이전트 도구는 아직 미숙하다 ([Manim config](https://docs.manim.community/en/stable/guides/configuration.html)).

엔진과 상관없이 지켜야 할 결정론 규칙이 있다. 라이브러리는 순수 `f(t)`를 제공하거나 일시정지된 인스턴스에서 seek가 가능해야 하고, 프레임 사이에 상태를 쌓으면 안 된다. CSS transition, framer-motion/Motion 컴포넌트, react-spring, R3F `useFrame`, 물리 엔진, 파티클 시스템은 이 조건을 어긴다. 이런 것들은 미리 "bake"하거나 시간 uniform을 `frame/fps`로 구동하도록 바꿔야 한다 ([Remotion third-party](https://www.remotion.dev/docs/third-party), [Remotion three](https://www.remotion.dev/docs/three)). Lottie는 expression 때문에 깜빡일 수 있다 ([@remotion/lottie](https://github.com/remotion-dev/remotion/blob/main/packages/docs/docs/lottie/index.mdx)). 모션 토큰은 Material 3에서 가져오는 것을 권한다. 지속시간 스케일(50~1000ms)과 standard `cubic-bezier(0.2, 0, 0, 1)`, emphasized-decelerate `cubic-bezier(0.05, 0.7, 0.1, 1)` 같은 값이 Apache-2.0 파일로 공개되어 있다 ([material-web tokens](https://github.com/material-components/material-web/blob/main/tokens/versions/latest/sass/_md-sys-motion.scss)). 이 값을 motionmaxxing의 12개 이징과 함께 하나의 토큰 파일로 합치면 된다.

## 한국어 내레이션과 자막은 Qwen3-TTS와 WhisperX 강제 정렬로 닫힌다

한국어 TTS는 라이선스 문제로 후보가 크게 줄어든다. **Qwen3-TTS**는 코드와 가중치가 모두 Apache-2.0이고, 지원하는 10개 언어에 한국어가 들어 있으며, 3초 음성 클로닝과 텍스트 설명으로 목소리를 만드는 VoiceDesign을 제공한다 ([Qwen3-TTS](https://github.com/QwenLM/Qwen3-TTS), [arXiv 2601.15621](https://arxiv.org/html/2601.15621)). **Fun-CosyVoice3**(Apache-2.0)는 9개 언어에 한국어를 포함하므로 A/B 비교 후보로 둔다 ([CosyVoice](https://github.com/FunAudioLLM/CosyVoice)). 반대로 **Kokoro에는 한국어 음성이 없다** ([VOICES.md](https://huggingface.co/hexgrad/Kokoro-82M/blob/main/VOICES.md)). explainroo와 TheoremExplainAgent가 Kokoro를 쓰기 때문에, 이 레포들을 그대로 가져오면 한국어 내레이션이 되지 않는다. 한국 회사 Supertone의 Supertonic은 아카이브되었고 회사가 해산했다는 2차 정보가 있으므로 API를 기반으로 삼으면 안 된다 ([supertonic](https://github.com/supertone-oss-archive/supertonic), [mirror note](https://huggingface.co/lnkiai/supertonic-3-mirror)). 관리형 API가 필요하다면 Channel Talk의 Korean TTS Arena가 호출하는 Typecast와 ElevenLabs가 현실적인 선택지다 ([Ko-TTS-Arena](https://huggingface.co/spaces/channelcorp/Ko-TTS-Arena/blob/refs%2Fpr%2F1/tts.py)). 한국어 품질을 비교한 신뢰할 만한 벤치마크는 없다. 그러므로 TTS 제공자는 인터페이스 하나 뒤에 숨겨서 언제든 교체할 수 있게 한다.

자막 타이밍은 **WhisperX**(BSD-2)로 잡는다. WhisperX는 한국어용 기본 정렬 모델로 `kresnik/wav2vec2-large-xlsr-korean`(Apache-2.0)을 지정해 두었다 ([alignment.py](https://github.com/m-bain/whisperX/blob/main/whisperx/alignment.py)). 핵심은 받아쓰기(ASR)를 하지 않고 **이미 알고 있는 대본을 강제 정렬**하는 것이다. 이렇게 해야 한국어 자막에 인식 오류가 섞이지 않는다. 단, 정렬 사전에 없는 문자는 타이밍을 받지 못한다. "2014."나 "£13.60" 같은 토큰이 그렇다 ([WhisperX overview](https://gotranscript.com/public/whisperx-fast-whisper-transcription-with-word-timestamps)). 그래서 숫자와 영문 약어를 한글 읽기로 바꾸는 정규화 단계를 TTS와 정렬 앞에 두고, 화면에 표시할 때 원래 표기로 되돌려야 한다. motionmaxxing의 `sync.mjs`도 단어 타이밍을 프레임에 맞추는 같은 일을 하며 기준 속도를 초당 2.5~3단어로 잡는다 ([SKILL.md](https://github.com/Tejashmakwana/motionmaxxing/blob/main/SKILL.md)). 비트 검출은 permissive 라이선스인 librosa(ISC)로 한다. essentia(AGPL-3.0)와 aubio(GPL-3.0)는 copyleft 의무가 따른다 ([librosa](https://github.com/librosa/librosa), [essentia](https://github.com/MTG/essentia)).

음악과 효과음도 라이선스로 걸러야 한다. 생성 음악은 **ACE-Step 1.5(MIT)**가 가장 안전하다. MusicGen 가중치는 CC-BY-NC-4.0이고, Stable Audio Open은 별도의 커뮤니티 라이선스다 ([ACE-Step-1.5](https://github.com/ace-step/ACE-Step-1.5)). 스톡 음원은 Pixabay, Mixkit, Freesound의 CC0 필터 결과만 쓰고, BBC Sound Effects와 CC-BY-NC 자료는 빼야 한다 ([cinevva guide](https://app.cinevva.com/guides/free-sound-effects-music)). 마지막 라우드니스는 엔진 밖에서 FFmpeg 2-pass loudnorm이나 ffmpeg-normalize로 맞춘다. 웹·유튜브 기준은 약 −14 LUFS / −1 dBTP다 ([editingtools.io](https://editingtools.io/loudness/)). 국내 방송 납품은 2014년 미래부 고시 「디지털 텔레비전 방송프로그램 음량 등에 관한 기준」에 따라 **−24 LKFS ±2 dB**를 맞춰야 한다 ([law.go.kr](https://www.law.go.kr/LSW/flDownload.do?flSeq=165037919)). 이 고시가 2026년 현재도 바뀌지 않고 유효한지는 확인하지 못했다.

## 권장 스택과 레포 구조: 6개의 승인 게이트와 2단 QA

추천 스택은 다음과 같다. **엔진**은 HyperFrames(버전 고정)다. 수식 장면만 ManimCE로 렌더해 알파 레이어로 합성한다. **애니메이션**은 GSAP 일시정지 타임라인과 three.js(시간을 프레임에서 받도록 구동), gl-transitions(MIT)를 쓰고, 토큰은 Material 3와 motionmaxxing 이징을 합친 파일 하나로 관리한다. **디렉션**은 motionmaxxing의 법칙, never-ship 목록, G0~G5 게이트를 HyperFrames의 story → SPEC → review 루프에 옮겨 심은 자체 SKILL.md로 만든다. **오디오**는 Qwen3-TTS(Typecast/ElevenLabs로 교체 가능), WhisperX 한국어 강제 정렬, librosa 비트 그리드, ACE-Step 1.5로 구성한다. **후처리**는 ffmpeg CLI를 직접 호출하고 ffmpeg-normalize를 쓰며 `web`과 `kr-broadcast` 두 가지 납품 프리셋을 둔다. 사용자 팀이 3명 이하이고 HyperFrames가 맞지 않는다고 판단되면, 같은 구조에서 엔진만 Remotion으로 바꾸면 된다. 디렉션과 QA 레이어가 엔진에 독립적이도록 설계하는 것이 이 구조에서 가장 중요한 점이다.

레포 구조는 단계마다 산출물이 파일로 남고, 각 파일이 사람의 승인 단위가 되도록 짠다. 이 패턴은 Code2Video의 outline→storyboard, Math-To-Manim의 `01_intent.json`~`06_scene_spec.json`, HyperFrames의 SPEC/STORYBOARD/REVIEW가 공통으로 쓰는 방식이다 ([Math-To-Manim](https://github.com/HarleyCoops/Math-To-Manim), [Code2Video](https://arxiv.org/html/2510.01174)).

```
motion-studio/
  CLAUDE.md                  # 단계 게이트 규칙: 승인 없이 다음 단계 금지
  .claude/skills/director/   # 자체 SKILL.md + references/ (법칙, never-ship, 한국어 타이포 규칙)
  tokens/motion.json         # 이징·지속시간·stagger·홀드 (M3 + motionmaxxing 수치)
  tokens/brand/<brand>.md    # frame.md 스타일 디자인 토큰
  projects/<slug>/
    00_brief.md              # 주제 + 디자인 컨셉 → dense brief
    01_storylines.md         # 3안 → [게이트 1] 하나 선택
    02_storyboard.md         # 비트 표: 역할·"buys"·카피·진입/퇴장·프레임  → [게이트 2]
    03_script.ko.md          # 내레이션 원고(정규화본 포함) → TTS → align.json → [게이트 3] 청취 승인
    04_stills/               # 가장 어려운 비트부터 스틸 → [게이트 4]
    film/index.html          # HyperFrames 컴포지션
    05_review/               # 반해상도 렌더, 컨택트 시트, REVIEW.md(P0/P1/P2) → [게이트 5]
    06_final/                # final.mp4, 믹스, NOTE.md(게이트 수치, 자기 인증 금지) → [게이트 6]
    assets.manifest.json     # 에셋별 출처·라이선스(NC면 빌드 실패)
  scripts/ (tts, align, beats, qa, mix, deliver)
```

QA는 두 단계로 나눈다. 1단은 결정론적 검사다. HyperFrames `check`의 `dead_stretch`(3초 넘게 변화 없음), `text_below_floor`(짧은 변의 2.6% 미만 텍스트), `first_frame_empty`, 그리고 90% 액션 세이프와 80% 타이틀 세이프 영역을 검사한다 ([review.md](https://github.com/heygen-com/hyperframes/blob/main/skills/hyperframes/references/review.md)). motionmaxxing의 G2·G3·G5 같은 수치 게이트와 ffprobe/ffmpeg로 하는 길이·코덱·라우드니스 측정도 이 단계에 넣는다. 2단은 시각 리뷰다. 컨택트 시트와 컷 스트립(컷 전후 −0.2~+0.2초), 360px 폰 너비 시트를 만들어 에이전트가 "낯선 사람이 보듯" 묘사하게 하고, 결과를 `t=… · 위치 · 문제 → 정확한 수정` 형식의 P0/P1/P2 목록으로 받는다. HyperFrames는 10점 만점 채점을 명시적으로 금지한다. "점수로는 고칠 것을 찾을 수 없다"는 이유다 ([review.md](https://github.com/heygen-com/hyperframes/blob/main/skills/hyperframes/references/review.md)). VLM 판정은 참고용으로만 둔다. 최고 성능 모델도 UI 글리치 검출률이 40%에 그쳤고 ([VideoGameQA-Bench](https://ar5iv.labs.arxiv.org/html/2505.15952)), 화면 속 텍스트가 주장하는 내용을 실제 시각 정보 대신 보고하는 "text-overlay hijacking" 현상도 보고되었다 ([alphaxiv 2604.17375](https://www.alphaxiv.org/abs/2604.17375)). 자막이 많은 한국어 영상에는 특히 불리한 약점이다. 레이아웃 결함을 코드 위치로 추적하려면 Code2Video의 **6×6 앵커 그리드와 점유 테이블**이 쓸모 있다. 각 요소가 차지한 앵커와 그 요소를 만든 코드 줄을 기록해 두면 VLM이 짚은 픽셀 문제를 해당 코드 줄로 바로 연결할 수 있다 ([arXiv 2510.01174](https://arxiv.org/html/2510.01174)).

"방송급"이라는 목표에는 기술적 한계도 하나 있다. 두 웹 엔진 모두 브라우저의 8비트 sRGB 합성을 거치고, 어느 엔진도 10비트, HDR, Rec.709 색 관리나 방송 규격 준수 도구를 문서화하지 않았다. 방송 TV 납품 사례도 찾지 못했다 ([HyperFrames vs Remotion guide](https://hyperframes.heygen.com/guides/hyperframes-vs-remotion)). 방송 납품이 실제 요구사항이라면 알파가 필요할 때 ProRes 4444 중간본으로 렌더하고 ([Remotion transparent videos](https://www.remotion.dev/docs/transparent-videos)), 색 태깅과 라우드니스 맞춤은 별도의 FFmpeg/NLE 단계에서 처리해야 한다.

## Conclusion

조사를 마치고 나서 질문 자체가 바뀌었다. 처음 질문은 "어떤 레포를 가져다 쓸까"였는데, 남은 질문은 "어떤 판단 기준을 직접 소유할까"다. 엔진 층은 이미 범용 부품이 되었다. HyperFrames와 Remotion은 같은 Chrome→FFmpeg 경로를 쓰고 둘 다 공식 에이전트 스킬을 갖고 있다. 아무 스킬 없는 Claude Code도 기본 검사를 통과한다. 남은 차이를 만드는 것은 수치화된 연출 법칙, 금지 목록, 렌더 결과에 대한 결정론적 게이트, 그리고 단계별로 사람이 승인하는 지점이다. motionmaxxing과 HyperFrames는 서로 독립적으로 같은 타이밍 원칙에 도달했는데, 이 레이어를 직접 소유할 근거로 볼 수 있다. 이전 Remotion 시도가 실패한 원인이 엔진이 아니라 이 레이어의 부재였다면, 엔진만 바꿔서는 같은 결과가 반복될 것이다.

현실적으로 할 일은 둘이다. 첫째, 공개된 벤치마크 중 브랜드 준수, 타이포 위계, 모션 품질을 채점하는 것은 하나도 없다. 그러니 첫 영상 몇 편을 만들 때부터 사용자의 승인과 거절 기록을 `taste/verdicts.md` 같은 파일에 쌓아 자체 평가 기준으로 삼아야 한다 ([motionmaxxing SKILL.md](https://github.com/Tejashmakwana/motionmaxxing/blob/main/SKILL.md)). 둘째, 한국어는 이들 레포 어디에서도 1급 시민으로 다뤄지지 않는다. 한글 줄바꿈, 숫자 읽기 정규화, 한국어 자막의 초당 글자 수 같은 규칙은 사용자의 레포에서 처음 정의된다. 이 규칙들이 다른 레포와 구별되는 차별점이 된다.
