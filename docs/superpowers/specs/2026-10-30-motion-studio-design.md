## 1. 의도와 이유

이전 시스템(Remotion 기반, 2026-10-30 삭제)의 결과물은 기술적으로는 돌아갔지만 "사람 손이 닿은 디테일이 채워지지 않은, 생략이 많은 미완성 느낌"이었다. 반면 Styles-20의 샘플 프롬프트만으로도 **짧은 루프 영상**(대상 하나 + 반복 모션 하나)은 괜찮은 품질이 나왔다.

결론: 효과를 만드는 능력은 이미 충분하다. 무너지는 곳은 그 위의 층이다.

1. **서사 층**: 키메시지가 먼저 있고, 스토리와 서사에 대한 고민이 선행되어야 한다. [사용자 결정]
2. **연결 층**: 컷과 컷이 서사로도, 디자인으로도(형태, 색, 위치가 다음 컷으로 넘어감) 이어져야 한다. [사용자 결정]
3. **구성 층**: 컷 안에서 요소의 자연스러운 배치와 움직임. [사용자 결정]
4. **테크닉 층**: 그다음이 테크닉이고, 여기서 디테일이 승부를 가른다. [사용자 결정]

이 원판의 투자는 1~3번 층(서사, 연결, 구성)의 규칙과 프로세스에 집중한다. 효과 층은 검증된 스타일 모듈을 재사용한다.

## 2. 목표, 비목표, 반목표

### 목표
- **범용 원판**: 주제, 영역, 용도, 길이, 화면 비율을 가리지 않는다. [사용자 결정] 장르별 규칙은 원판에 박지 않고, 0단계 대화에서 그 영상의 용도·시청자·길이·비율·톤을 확정해 이후 단계의 기준으로 삼는다.
- **주제 한 줄에서 완성본까지**: 리서치, 키메시지, 서사, 디자인 컨셉, 원고, 음악, 모션, 최종 렌더까지 레포가 끌고 간다. [사용자 결정]
- **대화로 채우는 단계 진행**: 사용자의 구체적 지침이 필요한 지점에서는 에이전트가 멈춰서 묻거나 대화로 아주 디테일하게 채운다. [사용자 결정] 각 단계에서 무엇을 물어야 하는지가 레포 안에 질문 목록으로 정의되어 있어야 매번 같은 깊이로 대화할 수 있다. [Claude 제안]
- **단계별 승인**: 각 단계를 보여주고 승인받기 전에는 다음 단계로 가지 않는다. [사용자 결정, 기존 원칙]
- **영상으로 판단**: 승인은 글이나 캡처가 아니라 미리보기 영상을 보고 한다. "결국은 영상이니까." [사용자 결정]
- **BGM이 뼈대**: BGM이 영상의 생명이고, 효과음은 키 모션의 화룡점정이다. [사용자 결정]
- **취향의 축적**: 사용자의 승인·거절과 그 이유가 쌓여서 다음 영상의 기준이 된다. [Claude 제안]

### 비목표
- 실사, 생성형 비디오 모델(Kling, Veo 등)로 장면 자체를 만드는 것.
- TV 방송·영화 배급용 납품. ElevenLabs Creator 요금제는 이 용도를 허용하지 않는다. "방송급"은 품질 수준을 뜻하고 배포 채널은 웹(유튜브, SNS, 웹사이트)이다. [Claude 제안, 사용자 요금제에서 도출]
- 다중 사용자, 웹 앱 형태의 GUI.
- 효과 자체를 새로 발명하는 것. 효과는 Styles-20과 HyperFrames 블록 등 검증된 것을 쓴다.

### 반목표 (기술적으로 돌아가도 실패인 것)
- 효과 데모를 이어 붙인 영상. 화면에 요소가 하나씩 떠오르기만 하는 "움직이는 슬라이드".
- 키메시지와 서사가 승인되기 전에 장면 코드를 쓰는 것.
- 에이전트가 자기 결과물에 점수를 매기거나 "좋다"고 스스로 인증하는 것.
- 상업 사용이나 공개 재배포가 안 되는 에셋이 조용히 섞이는 것.
- API 키가 공개 레포에 커밋되는 것.
- 최종 MP4 렌더에 사용자 PC CPU를 쓰는 것.

## 3. 제약

- **작업 환경**: Windows 11 PC, Claude Code 데스크톱 앱. 사용자는 Claude Code와 대화하며 진행한다.
- **레포**: GitHub **공개** 저장소. [사용자 결정] 고객사 작업이나 비공개 자료는 다루지 않는다. [사용자 확인] 따라서 영상별 작업물(브리프, 원고, 에셋)도 레포에 커밋한다.
- **비밀값**: 루트 `.env`에 ElevenLabs API 키가 있다. 절대 커밋하지 않는다.
- **ElevenLabs 요금제**: Creator. [사용자 확인] 웹 상업 사용 가능, 필름·TV·방송 불가.
- **PC 사용 범위**: 품질 검사용 프레임 캡처(컨택트 시트, 컷 스트립, 결정론 비교)와 HTML 미리보기는 PC에서 해도 된다. [사용자 결정] 금지되는 것은 전체 영상의 MP4 렌더다.
- **렌더**: MP4 렌더는 PC CPU가 아닌 무료 원격 인프라에서. [사용자 결정] 1순위는 GitHub Actions(공개 레포라 무료 분 제한 없음 — 구현 전 현재 정책 확인). [Claude 제안] 2순위는 Claude Code 클라우드 세션(실현 가능성 미검증).
- **미리보기 비용**: 미리보기는 HTML을 브라우저에서 재생해 본다. MP4는 HTML 미리보기를 통과한 뒤에만 렌더한다. [사용자 결정]
- **라이선스**: 모든 코드, 모델 가중치, 에셋은 결과물의 상업 사용과 공개 레포 재배포가 가능해야 한다.
- **언어**: 한국어가 기본이다. 한국어 타이포(줄바꿈 `word-break: keep-all`), 숫자·영문 약어의 한글 읽기 정규화, 한국어 자막이 1급 요구사항이다.

## 5. Styles-20의 역할 [사용자 확인: "응 맞아"]

- **디자인 단계의 어휘집**이다. 키메시지와 서사가 정해진 뒤, 이야기에 맞는 시각 언어 후보 1~3개를 근거(색, 모션, 질감)와 함께 제안할 때 참조한다. 서사보다 앞서지 않는다.
- 20선은 "장면"이 아니라 "효과"다. 영상 전체의 톤(색, 질감, 움직임의 성격)을 정하는 데 쓰고, 컷 안의 배치와 컷 사이 연결은 연출 규칙이 맡는다.
- 문서 자체의 규칙을 유지한다: 번호를 말해도 자동 제작하지 않는다, 한 화면에 모션 어휘는 1~2개.
- 각 스타일을 HyperFrames에서 재사용 가능한 **검증된 스타일 모듈**로 만들어 둔다. 20선이 모두 HTML·three.js·GSAP·SVG 기반이라 엔진과 맞는다. 원문 프롬프트의 "정사각형 카드, 무한 루프" 조건은 모듈화할 때 "임의 비율, 시간 구간 재생, 프레임 시크 가능"으로 바꾼다.
- 어휘집은 자란다. 영상을 만들며 사용자가 승인한 새 스타일이 목록과 모듈에 추가된다.
- 모듈 20개를 처음부터 다 만들지 않는다. 실제 영상에서 쓰일 때 만들고 검증해 쌓는다. [Claude 제안]

## 6. 제작 단계와 승인 게이트

모든 단계는 같은 형식을 따른다: **입력 → 에이전트 작업 → 사용자에게 묻는 질문 → 미리보기 → 승인 → 확정 산출물 파일**. 승인 전에는 다음 단계 파일을 만들지 않는다. 수정 요청은 "몇 초 지점의 무엇"처럼 시간 위치로 주고받는다. [Claude 제안, 사용자 확인]

|---|---|---|---|
| 0. 시작 대화 | 주제를 받고 용도, 시청자, 길이, 비율, 톤, 내레이션 여부를 대화로 확정 | 한 페이지 브리프 | `00_brief.md` |

| 2. 서사 | 서로 다른 스토리라인 3안 → 선택 → 컷별 설계표: 컷의 역할, 시청자가 믿게 될 것, 카피, **다음 컷으로 넘어가는 연결 요소(서사·디자인)**, 키 모션 표시, 대략 길이. 내레이션이 있으면 원고 초안 | 스토리라인과 컷 구성 | `02_story.md` |

### 단계 원칙
- **BGM은 3단계에서 확정한다.** 곡이 바뀌면 타이밍 전체가 흔들리므로 서사와 같은 무게의 승인 지점이다. 컷 전환은 강박과 구간 경계에, 키 모션은 강조점에 맞춘다.
- **효과음은 2단계 설계표에서 "키 모션"으로 표시된 순간에만** 붙인다. 모든 움직임에 소리를 붙이지 않는다.
- **HTML 미리보기와 MP4는 다를 수 있다.** 브라우저는 실시간 재생 중 프레임을 건너뛸 수 있다. 그래서 6단계에서 MP4를 한 번 더 확인한다.
- **단계 되돌리기**: 사용자가 이전 단계를 바꾸면 그 이후 산출물은 다시 승인받는다. 어느 단계부터 다시 할지 에이전트가 영향 범위를 설명한다. [Claude 제안]
- **이어서 하기**: 새 대화에서 "이어서"라고 하면 에이전트가 프로젝트 폴더의 마지막 확정 산출물을 읽고 현재 단계를 파악한다. 진행 상태는 파일에서 읽을 수 있어야 한다. [Claude 제안]

## 7. 품질: 연출 규칙과 2단 QA

### 연출 규칙 (director 스킬)
- 수치 법칙: 착지는 감속, 퇴장은 가속하고 진입보다 짧게, 움직임 위에서 컷, 오버슛은 드물게, 글자 stagger 약 1프레임, 엔드 홀드 0.6~1.4초 등. 출처는 motionmaxxing `SKILL.md`·`references/`, HyperFrames `references/motion.md`.
- **never-ship 목록**: 코너 라벨·카운터, 덱 레이아웃, 카렛 타이핑 헤드라인, 스탯 슬라이드, 슬로건 카피, 모든 요소에 같은 이징·같은 길이 등.
- **구성 규칙**(컷 안): 위계, 여백, 시선 흐름, 요소 수 상한. [빌더 재량: 출처에서 추출해 정리]
- **연결 규칙**(컷 사이): 매치 컷, 형태·색·위치의 이어짐, 전환 유형 선택 기준. [빌더 재량: 출처에서 추출해 정리]
- **한국어 타이포 규칙**: keep-all 줄바꿈, 한글 폰트 위계, 숫자 정규화.
- 규칙은 사용자의 승인·거절 기록에 따라 갱신된다.

### 1단: 결정론적 자동 검사
- HyperFrames `check`/lint: 정지 구간(`dead_stretch`), 최소 글자 크기(`text_below_floor`), 빈 첫 프레임 등.
- motionmaxxing 게이트 G0~G5 중 스크립트로 계산되는 것(평평한 프레임 연속, 엔드 홀드, DOM 린트 등).
- 세이프 영역(액션 90%, 타이틀 80%), 텍스트 넘침, 대비.
- 결정론 회귀: 같은 프레임을 두 번 렌더해 비교.
- 최종 MP4: ffprobe로 길이·코덱·해상도, 무음·정지 구간, 음량(−14 LUFS, −1 dBTP).

### 2단: 시각 리뷰
- 컨택트 시트, 컷 전후 스트립, (세로 영상이면) 폰 너비 시트를 만들어 에이전트가 처음 보는 사람처럼 묘사한다.
- 결과는 `t=… · 위치 · 문제 → 정확한 수정` 형식의 P0/P1/P2 목록으로 `REVIEW.md`에 남긴다. **점수는 매기지 않는다.**
- 비전 모델 판정은 참고용이다. 최종 판단은 사용자가 미리보기를 보고 한다.

### 납품 노트
`NOTE.md`는 게이트 수치를 인용하고 남은 한계를 적는다. 품질을 스스로 인증하지 않는다.

## 9. 라이선스와 보안

- `assets.manifest.json`에 모든 외부·생성 에셋의 출처, 라이선스, 상업 사용 가능 여부, **공개 레포 재배포 가능 여부**를 기록한다. 하나라도 불가하거나 비어 있으면 검사가 실패하고 진행을 멈춘다. 생성 음악·효과음은 모델·프롬프트·시드(있으면)도 남긴다.
- 무료 음원 사이트 중 "원본 그대로 재배포 금지" 조건이 있는 자료는 공개 레포에 원본을 올릴 수 없다. 이런 자료는 기본적으로 쓰지 않는다.
- `.env`는 `.gitignore`에 넣고, 커밋 전 비밀값 검사를 둔다.
- MP4 렌더에는 API 키가 필요 없게 한다. 생성(ElevenLabs 호출)은 PC에서 하고, 생성 음원은 커밋하지 않고 PC의 `media/<slug>/`에만 둔다. 원격 렌더에 키가 필요해지면 GitHub Secrets를 쓴다.
- **ElevenLabs 생성물의 공개 게시 가능 여부**는 구현 전에 약관으로 확인한다(11절). 유료 요금제 생성물의 소유권이 사용자에게 있어 공개 레포에 올려도 될 것으로 예상하지만 미확인이다. 확인 결과 허용되지 않는다(`docs/spike-report.md` C절). 레포는 공개로 유지하고, 생성 음원은 비공개 저장소도 쓰지 않고 PC에서만 관리한다. [사용자 결정 2026-10-31] 원격 렌더에는 음원을 올리지 않는다. 원격은 무음 MP4를 만들고 음원은 PC에서 섞어 `-c:v copy`로 붙인다(사용자 결정 2026-10-31 "합쳐서 보내봐", 6단계 계획 `docs/superpowers/plans/2026-10-31-motion-studio-stage6-final.md`). 암호화 임시 업로드는 음원이 든 MP4가 공개 레포의 Actions 아티팩트로 남아 쓰지 않는다. 음원이 든 완성본 MP4도 커밋하지 않고 `media/<slug>/`에 둔다.
- vendor로 가져온 외부 지식은 원 라이선스 파일과 출처를 함께 둔다.

## 10. 기억과 성장

- `taste/verdicts.md`: 단계마다 사용자의 승인·거절과 그 이유를 날짜·프로젝트와 함께 기록한다. 다음 영상의 제안은 이 기록을 먼저 읽는다.
- 반복되는 거절 이유는 director 스킬의 규칙이나 never-ship 목록으로 승격한다. 승격은 사용자에게 보여주고 승인받는다. [Claude 제안]
- 스타일 모듈과 Styles-20 목록도 승인된 것만 추가한다.

## 11. 구현 전에 확인할 것

- GitHub Actions: 공개 레포 무료 사용 조건, 작업 시간 제한, 아티팩트 크기·보관 기간.
- HyperFrames: 현재 안정 버전, Windows에서 미리보기(Studio) 동작, GitHub Actions 리눅스에서 헤드리스 Chrome 렌더 동작, MusicGen 폴백을 끄는 방법.
- **한글 폰트가 원격 렌더 환경에 설치되는지.** 미리보기에서 보이던 폰트가 헤드리스 렌더에서 빠지는 것은 알려진 실패 유형이다. 폰트 파일을 레포에 두거나 워크플로에서 설치한다(폰트 라이선스가 공개 재배포를 허용해야 함).
- ElevenLabs Creator 요금제에서 Music API, Sound Effects API 사용 가능 여부와 월 한도, 그리고 생성물을 공개 레포에 원본 파일로 올려도 되는지(9절).
- Beat This! 설치.
- Claude Code 클라우드 세션 렌더의 실현 가능성 (2순위라 원판 완성에 필수는 아님).

## 12. 구축 순서와 완성의 기준

### 구축 순서 [사용자 결정: 파일럿과 함께 단계별 구축]
- 원판을 한 번에 다 만들지 않는다. **파일럿 영상 하나**와 함께 단계별로 쌓는다. 원판 구축 자체도 단계마다 보여주고 승인받는다.
- 첫 작업은 **엔진 검증 스파이크**다. HyperFrames로 짧은 테스트 컴포지션을 만들어 (1) Windows 브라우저 미리보기, (2) GitHub Actions 리눅스에서 헤드리스 렌더와 한글 폰트, (3) MusicGen 폴백 끄기를 확인한다. 하나라도 실패하면 엔진을 임의로 바꾸지 않고 결과를 가지고 사용자에게 돌아온다. [Claude 제안]
- 그다음 0~2단계 도구(CLAUDE.md, 단계별 질문 목록, 산출물 템플릿, director 스킬의 서사·연결 규칙)를 만들고 파일럿으로 실제로 돌려 본다 → 승인.
- 이어서 3단계(애니매틱, BGM 생성·분석), 4단계(디자인 토큰, 스타일 모듈), 5단계(1단 자동 검사, 2단 시각 리뷰, 효과음), 6단계(원격 렌더 워크플로, 믹스·음량)를 파일럿이 그 단계에 도달할 때 만들고, 매번 파일럿 결과로 승인받는다.
- director 스킬의 규칙을 쓰기 전에, 휴지통에 있는 이전 시스템의 `lessons_learned.md`와 아트 디렉션 플레이북을 참고할지 사용자에게 묻는다. [Claude 제안]

### 완성의 기준
- 파일럿 영상이 0~6단계를 모두 통과하면 원판의 첫 버전이 완성된다. 파일럿 주제는 시작할 때 사용자가 정한다.
- 성공의 기준은 사용자가 완성본을 보고 "사람 손이 닿은 디테일이 채워졌다"고 판단하는 것이다. 기술적으로 렌더가 끝나는 것은 기준이 아니다.
- 파일럿에서 나온 거절 이유는 `taste/verdicts.md`와 규칙에 반영된다.

## 14. 향후 방향: 오케이스트레이션 하네스 [사용자 결정, 2026-10-30]

전체 제작 파이프라인을 계획할 때(3단계 이후 계획부터) **오케이스트레이션 형태의 하네스**까지 염두에 둔다. 단계별 작업을 전담 에이전트에 맡기고, 하네스가 단계 순서, 승인 게이트, 산출물 전달을 관리하는 형태다. 지금 만드는 구성요소는 하네스가 그대로 호출할 수 있게 둔다.
- 단계 상태는 파일(front matter `status`)과 `scripts/status.mjs`의 JSON 출력으로 읽을 수 있어야 한다.
- 단계마다 입력·산출물·게이트가 `stages/<단계>/`에 명시되어 있어야 한다.
- 스크립트는 사람 없이 실행 가능한 CLI(인자 입력, JSON 출력, 실패 시 non-zero exit)로 만든다.
- 사용자 승인은 하네스에서도 자동화하지 않는다. 승인 게이트는 사람에게 멈춘다.
